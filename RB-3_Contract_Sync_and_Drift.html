Before you start

When the contract changes, the Spring side and the Angular side must change with it. In this lab you make a deliberate breaking change, watch three different checks catch it before anything is merged, and write the pull request that explains it.

You need

  • RB-1 and RB-2 finished: payments-api and payments-ui side by side, both passing their tests.
  • A tool to compare two OpenAPI files. This runbook uses oasdiff; your trainer may have installed it. Step 4 shows how to install it, and a no-install alternative.
  • About 35 minutes. Work through the steps in order.

You will have at the end

  • A saved baseline of the contract and a changed version of it.
  • A comparison report that names the breaking change.
  • A failing backend test and a failing frontend build, both caused by that one change, and both fixed.
  • A pull request description with a contract section.

Words used in this runbook

  • Drift: the contract says one thing and one side still does another.
  • Breaking change: a change that makes existing clients or servers fail without any change on their side.
  • Baseline: a saved copy of the contract before the change, used for comparison.

Step 1: Prove both sides pass and save a baseline

A change can only be blamed for a failure if everything passed before it. Check both projects first.

  1. In payments-api run the backend tests (Windows: mvnw.cmd test):
    Terminal, in payments-api
    ./mvnw test
  2. In payments-ui run the frontend tests and build:
    Terminal, in payments-ui
    ng test --no-watch
ng build
  3. Save the baseline. In payments-api create a folder contract-baseline and copy the contract into it under a new name:
    Terminal, in payments-api (Mac or Linux)
    mkdir contract-baseline
cp src/main/resources/openapi/payments.yaml contract-baseline/payments.v1.yaml
    Terminal, in payments-api (Windows)
    mkdir contract-baseline
copy src\main\resources\openapi\payments.yaml contract-baseline\payments.v1.yaml

Check backend tests show BUILD SUCCESS, frontend tests and build pass, and contract-baseline/payments.v1.yaml exists. If anything is red, stop and call the trainer.

Why outside src The baseline lives next to the project, not under src/main/resources, so the generator never reads it by mistake. In a real team the baseline is simply the contract on your main branch.

Step 2: Sort six changes

Before you change anything, decide which kinds of change are dangerous. Mark each row Safe, Risky or Breaking, from the point of view of a client that already works against version 1.

#Change to the contractYour verdict
1Add a new optional field note to the request
2Rename the field amountMinor to amount
3Change payerAccountId from text to a number
4Make the optional request field reference required
5Add a new value REFUNDED to the response status list
6Change the success response from 201 to 200

Answers 1 Safe. 2 Breaking. 3 Breaking. 4 Breaking. 5 Risky: clients that list every status may not know the new one. 6 Breaking: clients that check for 201 will treat 200 as unexpected. Remember the checklist from the demo: removed or renamed fields, type changes, newly required fields, narrowed enums, changed status codes.

Check you can explain row 3 in one sentence. It is the change you make next.

Step 3: Make the breaking change

You play the backend developer who decides that payer account numbers are now numeric. Edit the one contract, and nothing else.

  1. Open src/main/resources/openapi/payments.yaml in payments-api.
  2. Find payerAccountId in CreatePaymentRequest and replace its lines so it reads exactly as below. The required list stays as it is.
    payments.yaml (inside CreatePaymentRequest, properties)
            payerAccountId:
          type: integer
          format: int64
          minimum: 1
  3. Change the contract version near the top from 1.0.0 to 2.0.0, because a breaking change deserves a new major version.
  4. Save. Check the Problems panel (Ctrl+Shift+M): Spectral should still show no errors.

Do not change any Java or TypeScript yet. The point is to see what the contract change does on its own.

Step 4: Detect it with a contract comparison

A comparison of the old and new contract finds the break before any code is built. Use Option A if oasdiff is installed; use Option B if you cannot install it.

Option A: oasdiff

  1. Check whether it is installed: run oasdiff --version. If it prints a version, go to step 3.
  2. Install it by one of these ways, then open a new terminal and repeat step 1 (oasdiff on GitHub):
    1. Mac: brew install oasdiff
    2. Mac or Linux: curl -fsSL https://raw.githubusercontent.com/oasdiff/oasdiff/main/install.sh | sh
    3. Any system with Docker: use the Docker form of the command in step 3 instead.
    4. Windows: download the Windows build from the oasdiff releases page on GitHub, unzip it, and put oasdiff.exe in your payments-api folder, or ask the trainer.
  3. In payments-api run the comparison of old against new:
    Terminal, in payments-api
    oasdiff breaking contract-baseline/payments.v1.yaml src/main/resources/openapi/payments.yaml
    Docker form (Mac or Linux)
    docker run --rm -t -v "$PWD:/specs" tufin/oasdiff breaking /specs/contract-baseline/payments.v1.yaml /specs/src/main/resources/openapi/payments.yaml
  4. Read the output. It lists each breaking change with a severity. You should see a message saying that the request property payerAccountId changed its type. The exact wording belongs to the tool.
  5. Run it once more with a failing exit code, the way a build pipeline would. The command must report a non-zero result (Apidog guide):
    Terminal
    oasdiff breaking --fail-on ERR contract-baseline/payments.v1.yaml src/main/resources/openapi/payments.yaml

Option B: compare in VS Code (no install)

  1. In the Explorer click payments.v1.yaml, then hold Ctrl (Cmd on a Mac) and click payments.yaml.
  2. Right-click either one and choose Compare Selected.
  3. Go through the six-row checklist from Step 2 against every highlighted line.

Check you can name the check that caught the change, which one field changed and how, and whether it is breaking. Copy the report line into your notes: you need it in Step 7. In a real team this same command runs in the pull request pipeline against the main branch.

Step 5: Regenerate both sides and watch them fail

The contract is the single source, so both generators now produce new types. Run each side and read the failure; do not fix anything yet.

Backend

  1. In payments-api run the tests. The generator runs first and rebuilds the DTOs from the new contract.
    Terminal, in payments-api
    ./mvnw test
  2. Read the end of the output. Expect BUILD FAILURE with failing tests in PaymentsContractTest. Note which tests failed and what each expected against what it received.
  3. Open the regenerated CreatePaymentRequest.java under target/generated-sources. Find the type of payerAccountId: it is now a number type.

Frontend

  1. In payments-ui regenerate the models, then build:
    Terminal, in payments-ui
    npm run generate:api
ng build
  2. Read the error. Expect a message that a string is not assignable to type number, pointing at payerAccountId in payment-form.ts.

What you just saw One edit to one file made the backend fail at test time and the frontend fail at compile time, with no runtime surprise. That is the benefit of generated types on both sides.

Think about it The contract says every 400 response uses the ApiError shape. When the backend rejected the old text value, Spring answered with its own error body instead. That is a second, quieter drift between the contract and the implementation. You are not asked to fix it today; write it down as a follow-up for the pull request.

Check you have the failing test names from the backend and the exact error line from the frontend written down.

Step 6: Fix both sides and prove it

Update the code to match the new contract with the smallest change that works. Use Copilot, but read every change it proposes.

Backend

  1. Open src/test/java/com/example/payments/PaymentsContractTest.java.
  2. In each request body change the payer account from text to a number, for example "payerAccountId": 1001 instead of "payerAccountId": "acc-1001".
  3. Run ./mvnw test. All tests must pass.

Frontend

  1. Open Copilot Chat, attach payment-form.ts, payment-form.html and payment-form.spec.ts, and paste in the comparison report line from Step 4 with this prompt:
    Copilot chat prompt
    The API contract changed: payerAccountId in CreatePaymentRequest is now an integer (int64, minimum 1) instead of a string. The generated types in src/app/api have already been regenerated. Update the PaymentForm component, its template and its spec to match, with the smallest possible change. The payer account control must hold a number, be required, have a minimum of 1, and use a number input. Update the test bodies and any validation message. Do not edit anything under src/app/api. After the code, list every line you changed.
  2. Apply the changes and compare them with Copilot's list of changed lines. If the diff touches more than it listed, or anything under src/app/api, reject it.
  3. Run ng build and ng test --no-watch. Both must pass.

Prove the loop is closed

  1. Run the comparison once more, but this time compare the new contract with itself. It must report no breaking changes. This shows the baseline is now stale: in a real team you would merge, and the new contract becomes the next baseline.
    Terminal, in payments-api
    oasdiff breaking src/main/resources/openapi/payments.yaml src/main/resources/openapi/payments.yaml

Check ./mvnw test, ng build and ng test --no-watch all pass, and no file under target/ or src/app/api was edited by hand.

Step 7: Write the pull request description

A reviewer should read the contract change first and the code second. Write the description below in a file named PR-description.md in payments-api, filling in the brackets from your notes.

PR-description.md
## Summary
payerAccountId in the Payments API changes from a string to a 64-bit integer.

## Contract change (read this first)
- File: payments.yaml, version 1.0.0 to 2.0.0
- Comparison result: [paste the oasdiff report line]
- Breaking for: [who: every client that sends payerAccountId as text]

## Impact
- Backend: DTOs regenerated. [N] contract tests failed before the fix; fixed in PaymentsContractTest.
- Frontend: models regenerated. The build failed before the fix; PaymentForm, its template and its spec updated.

## Rollout
- [Both sides must deploy together, or describe a transition period]

## Checks that caught it before merge
- Contract comparison: [result]
- Backend contract tests: [which tests failed, then passed]
- Frontend build: [error line, then clean]

## Follow-ups
- [Spring's default error body for unreadable requests does not match the ApiError contract]

## Verified and accepted
- What I verified, and how: [ ... ]
- What I accepted unchecked: [ ... ]

Check the description names the check that caught the break, says who is affected, and says how the two sides roll out. A reader who sees only this file should know whether the change is safe to merge.

Troubleshooting

SymptomFix
oasdiff is not recognisedOpen a new terminal after installing, or put oasdiff.exe in the payments-api folder and run .\oasdiff on Windows. Or use Option B.
oasdiff reports nothingCheck the order: the baseline comes first, the changed file second. Also confirm you saved the change in Step 3.
Backend tests still pass after the changeThe generator may not have rerun. Run ./mvnw clean test.
Frontend build still passesRun npm run generate:api again; the models only change when you regenerate.
Copilot changed files under src/app/apiReject that part and run npm run generate:api to restore the generated files.
Spectral shows errors after the editAn integer field cannot keep minLength or maxLength. Remove those lines from payerAccountId.

Completion checklist

Show the trainer this checklist, ticked, and keep PR-description.md for the graded home exercise.
